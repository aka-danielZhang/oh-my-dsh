## 教训一：合并旧远端线后必须全树 typecheck

fork 仓远端 master 停在 alpha.1 时代（rc.1 起的发布线一直在 feature 分支 tag 上，master 从未更新）。用 `-X ours` 对齐时，**冲突被裁决但可自动合并的旧代码 hunk 照样混入**，41+ 个源文件被污染（compaction-basic 类型错误由 pre-push typecheck 拦下）。`publish-fork --list` 与文档配对检查都发现不了这类污染——合并陈旧分支后必须立刻跑 root typecheck + 受影响包测试。

## 教训二：上游 rc 发布只 bump 改动过的包

上游 `release(dsh): 0.1.5-rc.2` 不改 `dsh-todo-completion-guard` 的 manifest（该包上游零变更），而 fork 发布面包含它 → `publish-fork.mjs --base` 断言 fail fast。好处是没有半发布态；坏处是 CI 空跑一轮。**每次基线 bump 后、打 tag 前，先核对 14 个 FORK_MODIFIED 包的 manifest 版本是否全部等于新基线**（本地 `node scripts/publish-fork.mjs --list` 之外再跑一次 dry-run 即可提前暴露）。
