# 2026-10-30 云之家 Sense 采集调度、容量与健康展示改造方案

> 状态：**待评审、待实现，仅设计**。针对实际运行中的 directory-capacity、init-boundary-unproven、round-deferred、directory-truncated 提示提出改造。本次不修改代码、实例配置、数据库或已安装 Desktop。
>
> 本文是在 [focused 设计 v2](2026-10-29-quno-sense-yzj-mentions-direct-design-v2.md) 与当前 0.2.0 实现基础上的后续决策记录，修订其轮次、容量和初始化方案；结构化 @、私聊 incoming、只读权限和事件身份规则继续沿用。当前行为仍以 [Quno 开发说明](../quno-bot-design.md) 为准，本文不表示功能已经上线。

## 1. 决策摘要

推荐改为：**持续推进的采集工作队列 + 按会话持久化游标 + 独立的分析合并窗口 + 进度/健康/覆盖三类展示。**

- Sense 限制的是对云之家的请求速率、在途请求、读取字节和提交批量；匹配事件采到即可提交，不为控制模型或通知频率而在 Sense 内等 5 分钟。
- “每 5 分钟”保留为默认的**近期活动发现周期**。已经发现的积压分片连续消化，下一片不再等完整周期。
- 取消“200 个会话就是全部可覆盖范围”的产品限制。200 改为内存缓存参考值，全部已纳入会话的游标由 Host 分条持久保存；仍设明确磁盘资源上限，不承诺无限容量。
- 初始化异常按原因诊断、退避与恢复；单个会话时间乱序不应无限占用队列头，更不能通过清空检查点解决。
- Quno 在事件入库后归并分析，通知仍由 outbox 统一节制。加快采集不会自动等于增加模型调用或主动汇报。

**范围变化必须明确**：彻底解决容量需要给 `dsh-quno` 增加通用的分条 checkpoint 能力及同事务提交支持，调整 SQLite；分析合并也属于 Quno 调度器。这修订了 v2 的“不改 Quno 核心、不加表”限制。Electron IPC、harness 和云之家写权限均无需改变。只改 Sense 的阶段可以先缓解调度，但不能宣称已解决覆盖容量。

## 2. 当前异常的含义与代码依据

| 提示 | 当前实际含义 | 改造目标 |
|---|---|---|
| directory-capacity：80 个会话未纳入 | 目录发现时遇到 200 会话硬上限；这 80 是该次扫描的拒收计数，不是已去重的全局总数 | 保留所有纳入范围的会话游标，报告真实去重数量；资源不足仍明确报未覆盖 |
| init-boundary-unproven | 初始化要求整页时间均可解析且升序；失败则提交空事件，仍未建立游标 | 区分时间解析、顺序与锚点问题；增加单条边界探测、退避及独立补采 |
| round-deferred：180 个未服务 | 本轮候选超过默认 20 个名额，剩余等待后续轮次 | 作为排队进度，持续续跑；超过等待阈值才升级为调度异常 |
| directory-truncated：下轮第 38 页 | 已在跨轮扫目录，尚未走到末页；不等于已经丢消息 | 正常显示扫描进度；停滞/超时/明确覆盖丢失才显示异常 |

对应实现入口：

- [index.ts](../../plugin/dsh-quno-collector-yzj/src/index.ts)：成功整轮结束后 `intervalSec` 计时，默认 300 秒。
- [checkpoint.ts](../../plugin/dsh-quno-collector-yzj/src/checkpoint.ts)：`MAX_SESSIONS=200`、160 KiB 序列化限制；Host 单值上限另为 200,000 字符。
- [round.ts](../../plugin/dsh-quno-collector-yzj/src/round.ts)：20 会话选择、初始化、目录扫描、逐批 ingest；全部 gap 拼成一条 degraded 文案。
- [messages.ts](../../plugin/dsh-quno-collector-yzj/src/messages.ts)：`lastMsgId` 被解析，但当前 round 没有使用它判断消息水位变化。
- [service.ts](../../plugin/dsh-quno/src/service.ts) 与 [scheduler.ts](../../plugin/dsh-quno/src/scheduler.ts)：事件入库后调用 `checkNow('event')`；单飞与每日预算已有，但事件入口没有按检查间隔做硬节流，运行结束的积压还会走约 1.5 秒 drain。

还存在几个与扩大额度有关的实现缺口，必须一起处理：

1. `lastAttemptAt` 在会话记录中初始化为空，却没有在每次服务时持续更新；初始化边界失败分支也未设置重试时间、失败次数或公平轮转位置。默认排序值长期为 0，坏会话可能反复抢前排。
2. needsCatchUp 的排序值也是 0；仅靠时间排序不能保证多个持续积压会话互相公平，需要显式轮转。
3. `unresolvedCount += addedDebt` 会将再次遇到的同一拒收会话重复累计，不能当“缺少多少个唯一会话”展示。
4. 白名单在目录纳入时检查，当前选择队列未重新排除已存在但后来移出白名单的群；修改范围应立即影响调度，而不是只影响新增目录。
5. 当前只记录了轮内事件花费，没有实际消费 `maxBytesPerCheck`；调度加速前必须补上字节预算。

这次仅依据用户提供的提示和仓库实现诊断；没有读取正式实例 checkpoint，也没有重新读取上述异常会话的聊天原文。因此不能断言三个初始化失败会话具体是“缺时间”还是“乱序”。

## 3. 三种节奏分别由谁负责

```mermaid
flowchart LR
  Y[云之家只读 CLI] --> C[Sense 请求预算与采集队列]
  C --> F[结构化过滤]
  F --> T[事件与游标同事务提交]
  T --> D[持久 Delivery]
  D --> S[Quno 合并窗口与模型预算]
  S --> O[outbox 去重与通知节奏]
  O --> U[主对话]
```

| 层 | 应负责 | 不承担 |
|---|---|---|
| Sense | 请求限速、源端退避、确定性过滤、游标、可靠提交 | 模型调用频率、通知安静时段、是否值得回复 |
| Quno Scheduler | 聚合待分析事件、自动分析最小间隔、单飞、每日模型预算 | 为降低模型费用而阻止来源事件入库 |
| Quno outbox | 同主题去重、主动通知配额、安静时段、用户是否正在对话 | 采集 checkpoint 和云之家读取调度 |

空事件 checkpoint/健康更新不能启动模型；来源 `p1` 也不直接获得立即分析或立即通知权限。

## 4. Sense：从整轮休眠改成持续工作队列

### 4.1 工作类型

一个实例只有一个调度器和一个提交者，内部有以下工作类型，不各自启动相互竞争的定时器：

| 工作 | 触发与默认目标 |
|---|---|
| 近期发现 | 启动立即执行，此后默认每 300 秒查询 recent 首页；支持显式改为 60 秒 |
| 目录续扫 | 从持久页码推进，每分钟目标 2 页；首次扫描和后续完整扫描均可跨分片持续执行 |
| 消息增量 | 新鲜 recent 水位变化、已有积压、到期探测时入队；有令牌就服务 |
| 新会话初始化 | 新发现且在授权范围内，逐会话进行，不等待全目录完成 |
| 冷会话探测 | 没出现在本次 recent 的已知会话默认 30 分钟后进入候选，实际等待由预算决定并显示 |
| 历史窗口补采 | 初始化留下的启用后窗口，低优先级、有限窗口，独立于后续增量 |
| 失败重试 | 到 retryNotBefore 才可调度；账号级失败暂停全部，单会话失败隔离 |

“30 分钟”是冷探测入队时间，不是万级会话全部完成探测的 SLA。待处理量超过请求容量时显示预计等待，不能把设置值当完成承诺。

### 4.2 请求与执行预算

以下为**待实测校准的默认值，不是云之家官方额度**：

| 参数 | 初始设计值 | 语义 |
|---|---:|---|
| CLI 并发 | 1 | 单账户顺序请求，先保证协议可追踪 |
| 账户请求桶 | 30 次/分钟，突发 2 次 | 计入 whoami、recent、message；同 Host 同 profile 的多个实例共享 |
| 单次 CLI deadline | 20 秒 | 结束时取消子进程，不把截断 stdout 当成功 |
| 分片预算 | 最多 20 次消息请求或 30 秒 | 到限主动让出执行权；这是执行分片，不是五分钟采集轮次 |
| 分片事件/提交字节预算 | 默认 200 条 / 2 MiB | 消费实际 UTF-8 序列化字节，包括 checkpoint patch，服从更低的 Host 限额 |
| 一次会话服务量 | 先取 1 页、20 条 | 有 more 则重新排队，其他会话有机会运行；空闲时可继续该会话 |
| 积压续跑间隔 | 目标 5 秒 | 与下一枚令牌、任务 dueAt、账号退避取共同约束，不强行每 5 秒发请求 |

没有到期工作就休眠至最早 dueAt；有工作则持续有限续跑，不存在“做完 20 个后无条件睡 300 秒”。每片结束允许 UI、取消信号及其他插件运行，避免忙等。系统唤醒只重建一次到期队列，不补发所有错过的 timer。

429 尊重可信 retry-after；没有时采用 1、2、4、8、16、30 分钟封顶退避并加小抖动；账号失败期间所有工作共享冷却，不让后台目录扫描继续撞限流。原始来源流量持续超预算时，保留游标和积压，显示延迟，不自动丢消息追最新。

身份在每个开始网络工作的分片前验证；身份请求也花令牌、包含在估算中。相同 profile 的多实例共享预算但各有 Source、游标和授权范围；其他进程调用 yzj-cli 的流量不受本 Host 控制，需要诚实说明。

### 4.3 公平性与水位优化

- 消息服务机会中，私聊/群聊各保留一半，空闲互借；每 lane 使用持久轮转位置 + dueAt，不把所有积压固定排成同一优先级前缀。
- 给目录/初始化/冷探测保留至少 20% 的可用请求机会，其他工作可借用空闲份额，不能让持续热群饿死发现工作。
- 每次尝试都记录 lastAttemptAt 和公平轮转位置，成功才更新 lastSuccessfulSyncAt。失败会话设置独立重试时间，不因“未成功”永远排第一。
- 新鲜 recent 的 lastMsgId 与已 ACK cursor 相同且无 gap/backfill 时，本次可免读消息；不同就排增量。旧缓存相等不能永久跳过探测。
- 同一 conversationId 只允许一个待执行增量任务，重复目录发现只更新目标水位，不追加重复任务。
- 每次入队和服务时都应用当前白名单；移出范围的群保留游标但停止请求。私聊仍按 focused 既定规则自动纳入。

初始化失败从 1、2、5、15、30 分钟退避，成功或新的可验证源端边界出现后允许重新评估。连续 3 次同一原因失败显示“此会话采集受阻”，其他会话继续。

## 5. 容量：游标持久条目与内存缓存分开

### 5.1 为什么不能只改 200

把 MAX_SESSIONS 调到 1000 仍受单个 JSON checkpoint 的 160 KiB/200,000 字符限制；每次推进一个会话还会序列化并写回整个目录。删除最旧会话游标让新会话进入则会丢失恢复位置，用户重新活跃时只能重新建基线。

推荐给 Host 增加通用 **keyed checkpoint** 能力，插件仍不接触 SQLite，也不 import Quno 存储实现：

- 小型根 checkpoint：版本、owner、focusedSince、目录扫描位置、调度配置版本。
- 每个会话一个 opaque 状态条目：游标、初始化/补采阶段、去重所需最小信息、dueAt、重试与 gap；Host 只认识条目键、版本及资源限额，不认识云之家字段。
- 内存只缓存近期使用的约 200 条，淘汰缓存不删除持久游标。重启按需分页读取，不将所有目录一次加载进内存。
- 拟议表 `sense_checkpoint_entries` 使用 `(instance_id, entry_key)` 唯一键；key 只用稳定 ID，不放正文。默认资源目标 10,000 条 / 50 MiB 每实例，先到者触发明确容量故障；发布前以 1,000 和 10,000 条基准验证，并据结果调整。

10,000 个状态可保存不代表能在五分钟内逐个轮询。存储容量与 API 吞吐必须分别展示。超过真实资源上限仍不得静默淘汰游标；缩小白名单是用户主动控制范围的选项，不再是 200 条之后的默认补救措施。

### 5.2 同事务接口草案

这是**拟议协议扩展，不是已有 API**。由 Host 显式声明 `checkpoint-entries/v1` 能力，支持受当前实例/generation 限制的分页读取与 `ingestBatch` 状态 patch。没有此能力的 Host 拒绝启动新版模式并明确要求升级，旧 Sense 的字符串 checkpoint 路径继续工作。

一次提交可以包含根 checkpoint 更新和若干条目 upsert/delete，使用实例级 checkpoint revision CAS，写者串行。事件、条目更新、根 revision 和批次回执必须在**同一个 Host SQLite 事务**内提交。ACK 同时确认这四者，batch hash 包含完整 patch。

- 仍保持每批 ≤100 事件、≤1 MiB、单事件 ≤64 KiB；额外建议每 patch ≤100 条状态、单条状态 ≤8 KiB。更大的目录拆批提交。
- 目录页中新发现条目全部 ACK 后才能推进目录页码；中途崩溃重读该页，upsert 幂等，不能只保存“下一页”而没保存会话。
- 分页读取状态返回 checkpoint revision；恢复装载期不发起写入，若外部 revision/generation 改变则重新对账，避免混合两个快照。
- 重试复用冻结 body/batchKey；旧 generation、CAS 冲突处理不变。
- 禁止插件自己另建 JSON/SQLite 文件，再用主库 checkpoint 指针声称同事务：那会引入两份持久状态不一致的窗口。

### 5.3 升级与回滚

先发布 Host 能力，再发布依赖它的插件。原 v2 owner、focusedSince、全部 cursor、gap、调度状态原样迁移；不得顺手重新建立基线。迁移时暂停该实例写者，旧 blob 作为只读迁移快照保留，分批幂等插入后以最终事务切换根 checkpoint 版本/迁移标记，验证条目数量与摘要一致才启动采集。

迁移中断可从旧快照重试，不清空历史。新版本开始推进后，旧快照已过时，**不能直接恢复旧 blob 继续采集**；需要导出当前条目重建旧格式且满足旧容量才可运行旧插件，否则暂停实例并保留数据。Host 缺能力或回滚不能触发静默丢弃条目。

## 6. 初始化：消息时间与分页边界分别处理

### 6.1 先诊断，再决定能否前进

将当前单一 init-boundary-unproven 拆为：time-missing、time-format-unsupported、page-order-unverified、anchor-mismatch、invalid-message-id。记录诊断数量、CLI 版本、字段类型、边界 ID/时间，不落聊天正文。没有真实响应证据前，不把某种猜测写为根因。

时间用于判断“是否早于 focusedSince”，msgId 用于遍历。整页时间升序只是辅助证据，不能等同于源端游标顺序；同理不能通过按时间排序后挑最大 msgId 来构造安全边界。

### 6.2 边界探测与恢复

对已有 cursor 的会话继续从原位置增量，禁止重新初始化。对确实未初始化的会话：

1. 获取 `newest --limit 1` 的最新消息锚点 A；该命令语义与空结果需做真实只读验证，列为发布门。一条消息不需要“全页时间升序”才能知道其来源声称的最新边界。
2. 将 A 作为待提交的前向起点，同时持久化独立补采任务及固定上界 A。首次启用时间到 A 之间的潜在消息不能因为建立前向 cursor 就当作已覆盖。
3. A 之后走 `new`；补采任务从 A 向 `old` 方向逐页读，A 本身也纳入补采/去重范围。两条路径提交同样的稳定 eventKey，事件与各自进度同事务提交。
4. 对页内顺序没有证明的来源变体，退回 `limit 1` 的相邻消息遍历，在源端不含锚点和相邻语义经验证后才推进；多条页不能靠本地重排序修复。已验证 adapter 可恢复较大页，提高吞吐。
5. 补采默认最多 200 条/会话、分片执行；额度耗尽或保留窗口不够则留下“启用后历史覆盖不足”的持久 gap。该上限影响历史补采，不阻止 A 之后的新消息采集。
6. 时间早于 focusedSince 不能在源端时间并非单调时自动充当完整补采停止条件。只有已验证的排序契约才允许按时间提前停止；否则读到固定预算/来源末端，并保留覆盖未知。

时间缺失但新鲜的、基于已持久前向游标读取的消息，可以保留 `occurredAt:null` 并按过滤规则接收；初始化补采中时间未知的消息无法区分历史与启用后，则记 gap，不默默将全部历史推给模型。

当 newest/limit1 也无法给出稳定 msgId、与重复探测发生无法解释的矛盾时，隔离该会话并退避；不能把“单条请求”当作跳过协议验证的理由。消息期间持续到达不是错误，固定 A 用于限制补采范围，A 后的新消息交给前向链路。

空会话保留显式 empty 状态；后续出现 A 时仍按以上方式处理，不把“之前为空”推导为“当前窗口一定装下所有新消息”。

## 7. Quno：事件及时落库，分析按窗口合并

当前 `onIngest → checkNow('event')` 会尝试立即运行，不能只靠调低 Sense 请求量来控制模型成本。建议给 Scheduler 增加自动分析准入：

- `onIngest` 完成无模型路由并标记有工作，调用自动调度入口，不直接走用户“立即检查”的强制路径。
- 首条 ready Delivery 建立固定 **15 秒合并窗口**，后续事件不不断延长它。
- 普通自动分析最早时间 = `max(firstReadyAt + 15 秒, lastAutoAnalysisStartedAt + checkIntervalSec)`；现有 checkIntervalSec 默认 300 秒，作为普通自动分析最小启动间隔。
- 每次启动读取当前已就绪 Delivery 集合，受单轮事件/token/每日模型预算约束；运行期间的新事件留到下一次准入，不重入。
- 当前 1.5 秒 drain 可以继续作为无模型检查提示，但不得绕过上述自动分析间隔。积压大时展示待分析量，不在 Sense 内扣留事件。
- 到期事项、可信 P0、用户立即检查按独立策略处理：手动触发可绕过合并窗口但不绕过暂停、单飞和每日预算；P0 仍需可信来源/规则准入，来源 `p1` 不可自行升级；到期事项按其 dueAt 唤醒，并与同次分析合并，不能再等待普通 5 分钟窗口。
- firstReadyAt/准入边界由持久 Delivery 和运行记录恢复，nextCheckAt 为持久目标；重启不能重置冷却并形成调用突发。手动/紧急分析若已经消费普通积压，也更新相应分析边界，避免紧接着多跑一轮。

通知沿用 [权威说明](../quno-bot-design.md) §10 的 outbox 去重、安静时段和配额；本改造不新增 Sense 通知器。分析间隔、事件接收、通知间隔在 UI 上分别命名，避免都叫“发送频率”。

## 8. 状态展示：进度、当前故障、历史覆盖缺口

### 8.1 分类

| 情况 | 展示 | 顶层健康 |
|---|---|---|
| 目录正常跨页推进 | “正在发现会话，已扫描 37 页，下次从 38 页继续” | healthy，可附“初始化中”进度 |
| 180 个到期任务等待，队列持续前进且未超时 | “待检查 180 个，最早等待 X 分钟” | healthy，进度信息 |
| 最老活跃任务等待超过 10 分钟，或目录 15 分钟无进展 | “采集延迟／目录扫描受阻” | degraded；阈值可配置 |
| 单会话初始化持续失败 | “3 个会话采集受阻，下次重试 X” | degraded，详情列原因；其他会话进度继续 |
| 明确未纳入范围/存储额度不足 | “部分会话未覆盖：X 个” | degraded，不能仅隐藏提示 |
| 补采窗口不足、过去相关性 unknown | 单列历史覆盖缺口及范围 | 独立于当前连接状态；仍有未处理影响时健康保留 degraded |
| 登录失效/限流/网络故障 | 现有分类与明确恢复操作 | auth-required / rate-limited / unavailable |

“队列已排空”只表示当前已发现工作处理完，不等于全局消息零遗漏。目录未知总量时只展示扫描页数和已发现数，不编造百分比或把 `count` 当总数。

### 8.2 指标与消除条件

健康 payload 拟增可选的结构化 progress / issues 字段（属于 Host schema、API 类型及 UI 的同步扩展，旧字段继续兼容），至少包含：trackedConversations、pendingConversations、blockedConversations、oldestPendingAt、lastDirectoryProgressAt、lastSweepCompletedAt、nextDiscoveryPage、requestBudget、checkpointBytes、nextRetryAt。

- pending 按唯一会话计，后台扫描页与前向/补采工作在详情分列；不能把请求数当会话数。
- 未纳入数按 conversationId 去重。若拒收 ID 的诊断集合本身超限，显示“至少 N 个／精确数未知”，禁止循环累加伪装唯一数量。
- 进度消息只更新计数，不每片拼接一长串群名；初始化错误按原因归组，详情才显示受影响会话。
- 当前故障修复后自动恢复；历史覆盖缺口只有补采完成或用户明确接受未覆盖范围后才归档。接受缺口不补造已采集证据。
- 移出白名单造成的未覆盖属于授权范围变化，显示范围说明，不继续当源端故障重试。

示意文案（数值仅为合成示例）：

> 云之家：正在同步。已跟踪 680 个会话，待检查 42 个，最早等待 2 分钟。目录已扫描 37 页。3 个会话初始化受阻，其他会话正常；查看详情。

不把同一实例中的正常进度全塞进“当前异常”，也不把真实未覆盖包装成“稍后即可完成”。

## 9. 配置迁移与实际吞吐

| 现有设置 | 新口径 |
|---|---|
| intervalSec | 保留持久值，映射为近期活动发现周期，默认仍 300 秒 |
| maxConversationsPerCheck | 迁为执行分片规模参考；不再决定整轮后必须休眠；新配置明确区分消息请求数与唯一会话数 |
| maxDiscoveryPages | 迁为单次目录任务页数上限，续扫按队列和请求桶推进 |
| maxPagesPerGroup | 迁为单次会话连续服务上限；默认先 1 页轮转，总量受账户桶约束 |
| groupIds | 授权群范围；立即影响已有/新增会话，移出不删 cursor |
| freshnessThresholdSec | 用于有工作时的延迟判断，不把长期无人发言当采集陈旧 |

新增加的请求预算与分析合并参数放高级设置，常用界面只保留“发现频率”“群范围”和同步进度。selected-groups 原始消息语义、Source、eventKey 均不变；旧实例迁移不静默重新采集历史。配置改动依然走旧 generation 撤销、停止、存新 revision、重启的 Host 流程。

吞吐预估必须注明前提：旧逻辑假设 200 个会话都需服务、每轮恰好能轮换 20 个，每轮后等待 5 分钟，轮转量级已约 50 分钟，且未计网络/失败；当前饥饿问题还可能更慢。新逻辑在 30 次/分钟、单页/会话的理想情况下，仅 200 个消息请求就至少约 6.7 分钟，另需身份、目录、重试，不能承诺 5 秒扫完。

改造收益主要来自：新鲜水位跳过无变化会话、发现与处理解耦、已有积压不再整轮休眠、失败会话不抢队列。1,000 个会话都每 30 分钟强制探测需要约 33 次/分钟，仅此已经超过默认桶，因此必须依据实际负载显示滞后并调整预算/探测周期，不用更高并发掩盖来源容量不足。

## 10. 实施阶段与验收门

### A. 先修调度与诊断（保持现有持久格式）

补 lastAttemptAt、失败退避、轮转公平、水位跳过、白名单重新校验、请求/字节预算、唯一计数；队列分片连续推进；正常目录进度不报故障。只在新读取任务处应用加速，ACK/事件语义不变。**此阶段仍受原存储容量限制，不能移除真实 directory-capacity 告警。**

### B. Host 分条 checkpoint 与迁移

增加通用能力、同事务 patch、迁移门禁和按需恢复，启用更大持久会话目录。修改范围为 Quno types/contracts/store/ingress/senses 和云之家 checkpoint adapter；不把云之家字段写进 Host 接口。完成此阶段才可解除 200 会话的覆盖限制。

### C. 边界恢复、分析合并与 UI

补 limit1 源端语义验证、前向/补采独立状态机、当前异常/覆盖历史分离；增加 Scheduler 自动准入和结构化状态展示。分析合并可先于采集加速上线，避免过渡阶段模型调用突增。

验收必须覆盖：

1. 1,000 会话目录、100 页 recent、页间移动/重复：无 200 处截断；所有符合范围的条目最终可调度，缓存淘汰不丢 cursor。
2. 200 个到期会话与 3 个永久初始化失败会话：失败任务遵循退避，正常会话有界轮转；连续热群不垄断队列。
3. 虚拟时钟验证 300 秒发现 + 5 秒续跑、30/min 令牌、单飞、账号共用桶、429、休眠恢复、暂停/HMR 取消；任意窗口实际调用和字节不超预算。
4. newest/limit1、new/limit1、old/limit1 的只读语义和源端异常；时间乱序不以排序造游标，补采不足始终显示覆盖 gap。
5. 事件/状态 patch/回执同事务：ACK 丢失、任意提交点崩溃、旧 generation、CAS 冲突、迁移中断均不跳 cursor、不多建事件；恢复从最新已提交状态继续。
6. 每片重复遇到同一个拒收会话不会增加唯一计数；白名单缩小后旧群停止被请求，恢复范围沿用 cursor。
7. 高频入库 100 批事件：及时落库；普通自动分析受固定合并窗口和最小间隔约束；用户立即检查、到期事项、可信紧急事件按各自规则；空批次零模型调用。
8. UI 将目录续扫/正常排队显示为进度，真实采集阻塞显示为故障，历史缺口不可被安静轮次抹除；接口旧客户端能忽略新增可选字段。
9. scratch Home 下完成升级、真实 SQLite 故障注入、停止/重启、1,000/10,000 条资源基准，再更新权威契约和包 README；不得手改正式 Profile 代替验收。

以上是计划中的验证，不是本次已执行结果。本次只核对代码、形成方案并更新文档索引；没有运行来源采集、变更频率或实施迁移。
